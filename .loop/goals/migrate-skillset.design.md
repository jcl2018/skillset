## Problem Statement

skillset adopted the workflow loop at template v0.27.29. The template is now frozen at v0.27.58 (Gate A). `setup.py
migration-check` on origin/main (486dd5d) reports 14 gaps:

| Class | Gap | Closed by |
|---|---|---|
| MIG_FILES | `.loop/START.md`, `CLAUDE.md` and `AGENTS.md` have a stale workflow-loop block | `update.py --apply` (sync runs `entry.py write` and `agents.py wire`) |
| MIG_SETTINGS | no `automation` in `.loop/config.json` | `update.py --apply` (sync runs `settings.fill_repo`, which declares the three built-ins) |
| MIG_AUTOMATION | health, regression and digest email are not declared | the same `fill_repo` |
| MIG_AUTOMATION | `regression_runs` is not `mac` while `regression_cron` is on | set `regression_runs` to `mac` |
| MIG_CHECKS | `regression.yml` does not trigger on `pull_request` | `regression_runs: mac`. The rule skips a mac repo, because "a mac repo's pr lane posts the statuses itself" (template copy `workflow-health/scripts/enforce.py`, `checks_gaps`). A mac repo needs a land row instead, and `.loop/regression.tsv` has 25 |
| MIG_BLOCKS | the Settings block in `docs/wiki/Home.md` and `README.md` is missing or stale | `render.py blocks` |
| MIG_FORMAT | Home has 2 commits since the page was last audited | `docs.py audit`, then fix what it names |
| MIG_WIKI_STALE (state) | published Bass-tab and Tests differ from `docs/wiki` | `docs.py publish`, done by the owner after the merge |

The PR closes all 12 PR-closable gaps, or 11 if the Home audit names a reviewed requirement line (step 5). In that case MIG_FORMAT stays open and is listed as owner-pending. The 2 state gaps close when the owner publishes after the merge.

## What Makes This Cool

The repo stays the same: the skill, its tests and every reviewed requirement line are untouched. Only the loop's
generated files and settings move to the frozen format. Every fix is the command migration-check prints for it, so the
migration is repeatable and the same recipe works for the next repo.

## Constraints

- Work only on files under `touches` (`.loop`, `.github/workflows`, `docs/wiki`, `README.md`, `CLAUDE.md`,
  `AGENTS.md`). Never touch `skills/bass-tab`, since goal lyric-layout may be editing it.
- Run every tool from the template copy at `~/.workflow-loop/template-v0.27.58/skills/...`, not from the installed
  skills, which link to the live template checkout.
- The repo is public, and GitHub Actions cannot run here (billing).
- No private name, path or email in commits. The goal file quotes the template copy path only in its home-relative
  form, which names no user.
- Never delete a wiki page, and never publish one: both are owner-only, after the merge.
- Reviewed requirement wording (the Bass-tab PRD criteria and Home's reviewed lines) must not change.

## Premises

1. The fix for each gap is the command migration-check prints, and the template's tools write the format. Hand edits
   are only for what no tool writes. Agreed (recommended).
2. Regression runs on this Mac (`regression_runs: mac`), even though the repo is public. Migration-check wants `mac`
   whenever `regression_cron` is on, public or private, and the settings reference allows "a public one recorded mac".
   Actions cannot run here anyway. This is the choice the operation session asked to have named, and it reads against
   done line 4's "GitHub Actions every 4 hours for a public one". It is recorded in the PR body as the deviation, chosen
   for consistency with migration-check. Agreed (recommended).
3. `regression_cron` moves from `17 9 * * *` to `17 */4 * * *`, and that is not an owner override. `17 9 * * *` was the
   template's default when skillset adopted on 2026-11-09 (skillset commit d72046c). Evidence: at template commit
   17017962, the last main commit before that adoption, `skills/workflow-setup/scripts/settings.py:35` reads
   `("regression_cron", REPO, "17 9 * * *", ...)`. Template commit a23c1255 (2026-11-10) moved the default to
   `17 */4 * * *`. Today's README labels the value "overridden" only because it compares against today's default. Done line 4 asks for every 4 hours. Every other value in
   `.loop/config.json` that differs from a default (agent_command and its model, cadence "30", auto_merge,
   review_depth, judge_env, digest_mail, smtp_*, risky_paths, and the rest) keeps its value byte for byte (done
   line 2). Agreed (recommended).
4. "The routine registry" in done line 5 is the `automation` list in `.loop/config.json`, which is what the Automation
   table reads. skillset owns no routine of its own. Health, regression and the digest are the template's built-ins and
   run through one Mac task, so `automation` holds exactly those three, each with its on/off state, cadence, where it
   runs (mac) and last run. Agreed (recommended).
5. `.loop/routines.tsv` (the DOC-16 registry of feature-owned routines, each needing a `### routine` runbook on its
   feature page) stays absent. skillset has no feature that owns a routine. The runbooks for health and regression live
   on the template's Health and Regression pages, under `### health-round` and `### regression-round`. Done line 7 is
   met by linking each Automation row to the runbook that governs it, through the entry's `does` text, a field the
   renderer prints verbatim. Agreed (recommended).
6. Wiki pages that are stale or old-format are listed in the PR body, with the command the owner runs after the merge.
   Nothing is deleted. Agreed (recommended).

## Approaches Considered

### Approach A: tool-driven migration (recommended)
- **Summary:** run `update.py --apply --from <template copy>` and merge its `workflow-update-v0.27.58` branch into the
  goal branch. Then apply each remaining fix migration-check prints (`regression_runs`, `regression.py workflow`,
  `render.py blocks`, `docs.py audit`), add the runbook links to the automation entries, and rerun migration-check
  until only the 2 owner-only state gaps remain.
- **Effort:** S. **Risk:** low.
- **Pros:** generated files come from the template's writers, so the next check and the next update agree with them.
  The recipe is repeatable on the other repos.
- **Cons:** `update.py` cuts its own branch, which needs one merge into the goal branch. The local
  `workflow-update-v0.27.58` branch is deleted after that merge (step 1).
- **Reuses:** update.py/sync.py, settings.fill_repo, entry.py, agents.py, render.py, docs.py, regression.py.

### Approach B: hand edits
- Write the blocks, settings and workflow by hand to match the check. Rejected: it duplicates the template's writers,
  and the next `update` would rewrite and fight them.

### Approach C: re-adopt from scratch
- Run `setup.py` again as if adopting. Rejected: it risks rewriting reviewed pages and owner settings, which breaks done
  line 2.

## Recommended Approach

Approach A, in this order:

1. `update.py --apply --from ~/.workflow-loop/template-v0.27.58 --repo .`. The skills half is skipped because the copy
   is a checkout (UPDATE_CHECKOUT). Local main is fast-forwarded to origin/main
   (486dd5d) first. The repo half then cuts `workflow-update-v0.27.58` from main and fills the missing
   settings, `template_version` 0.27.58, START.md and the agent blocks. Merge that branch into `loop/migrate-skillset`,
   then delete the local `workflow-update-v0.27.58` branch. A merged branch with an older base config makes the next
   update refuse (UPDATE_BRANCH_MERGED) until the goal merges, so deleting it avoids that state.
2. In `.loop/config.json`, set `regression_runs` to `mac` and `regression_cron` to `17 */4 * * *` (premises 2 and 3).
   Check that every other key's value is unchanged against origin/main with a scripted diff.
3. Run `regression.py workflow` from the template copy. With `regression_runs: mac` the writer writes nothing; it maps
   mac to its private path and prints `NOT WRITTEN` plus `REMOVABLE: .github/workflows/regression.yml is ours ...`.
   `git rm .github/workflows/regression.yml`. This leaves one regression home (the Mac, every 4 hours) and no stale
   09:17 Actions schedule that would run twice. It also stops a scheduled run that fails on billing every day. After
   this, a PR in skillset carries no GitHub Actions check: the goal's pr lane posts its statuses (AUT-2), and auto_merge
   reads those, so nothing waits on a check that cannot start. This path matches risky_paths `^\.github/`, so the PR
   body names the removal under its own heading.
4. Health, regression and digest email, as `fill_repo` declares them (step 1): each gets `runs: mac:skillset-health-regression`
   (`workflows.task_name`) and its cadence. Health takes `health_cron`, `47 */4 * * *`, every 4 hours. Regression takes
   `regression_cron`, every 4 hours after step 2. The digest email is enabled: `fill_automation` turns it off only when
   `digest_mail` is `off`, and `digest_mail` stays `cloudflare` (done line 2). The renderer shows each as `on (declared)`
   on "this Mac (launch agent skillset-health-regression)". The task itself is this Mac's existing Claude scheduled task
   `skillset-health-regression`, which runs health, the nightly regression suite and one digest email every 4 hours.
   It is machine state outside the PR. migration-check's MIG_TASK accepts it as the repo's local task, and the digest's
   mail keys live in the private flow file outside git. `fill_automation` keeps an entry that is already set, so the
   next update keeps edited text. Give each entry's `does` a runbook link, which the renderer prints verbatim:
   - health: `[runbook](https://github.com/jcl2018/agent-workflow-template/wiki/Health#health-round)`
   - regression: `[runbook](https://github.com/jcl2018/agent-workflow-template/wiki/Regression#regression-round)`
   - digest email: the Health link, because the digest runs in the health round.
5. `render.py blocks` for Home and README (Settings and Automation), then `docs.py audit` for Home, fixing only what it
   names in generated blocks or loop prose. If the audit names a reviewed requirement line, leave that line unchanged
   and list the finding in the PR body as owner-pending. MIG_FORMAT then stays open and is reported as such. It is not
   counted as closed.
6. `criteria.py render` and `docs.py check` stay green. The regression rows run green. Run `migration-check` (online)
   and record that it shows only the two state gaps, plus `migration-check --pr` exit 0. The one exception is step 5's
   case: there `--pr` reports only MIG_FORMAT for Home, and the full check reports MIG_FORMAT and the two state gaps.
7. List in the PR body the stale published pages (Bass-tab, Tests) and any published page with no source in
   `docs/wiki`, with `docs.py publish` for the owner after the merge. Delete nothing.

  MIG_WIKI_STALE gaps. The one exception is step 5's case: `--pr` then reports only MIG_FORMAT for Home, which is
  listed in the PR body as owner-pending.
- `git diff origin/main -- skills/` is empty, and no reviewed requirement line changes in `docs/wiki`.
- Every pre-existing config value is unchanged except `regression_cron` (a stale default), `regression_runs` (was
  unset) and the keys the template adds.
- README and Home Automation show health, regression and digest email as `on (declared)`, on this Mac (task
  `skillset-health-regression`): health and regression every 4 hours, the digest with each health round. Each row links
  to its runbook. "Last run" shows the renderer's pointer (`docs.py automation`) and not a live time, because a live time
  would change the page on every run.
- `.github/workflows/regression.yml` is removed, and nothing in skillset runs on GitHub Actions.
